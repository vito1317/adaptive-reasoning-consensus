# G1 窗口閘門報告：程式碼生成的窗口實測

> 直接量測，非文獻重建。40 題 LeetCodeDataset Medium/Hard × 8 個 Haiku 候選解，
> 318 個候選在沙箱中對隱藏測試套件評分。重現：`experiments/run_g1_window.py`。

## 判定：**未通過**（窗口 7.5% < 閘門 15%）

| 量 | 值 |
|---|---|
| 每候選通過率 pass@1 | 0.697 |
| 基線（最大行為叢集） | 30/40 = 0.750 |
| oracle（任一候選正確） | 33/40 = 0.825 |
| **窗口 = oracle − 基線** | **3/40 = 0.075**，CI95 (0.026, 0.199) |

對照：HumanEval+/MBPP+ 實測 3.56%；QA 計畫薄窗 2–5%；
審查者從 ACES 表格**重建**的 LeetCodeDataset 值 24–27%。
**我的直接量測（7.5%）遠低於重建值**，差異來源是候選預算：
重建假設 n≈200，我測 n=8。見下節。

## 題目形態：與 QA 計畫同構

| 形態 | 題數 | 說明 |
|---|---|---|
| 基線已正確（飽和） | 30 (75%) | 方法無事可做 |
| 無任何候選正確（能力牆） | 7 (18%) | 池中沒有正解，聚合無能為力 |
| **窗口（可救援）** | **3 (8%)** | 唯一能改變結果的分層 |

這正是 TACT 論文薄窗章節的結構：題目從「飽和」直接跳到「能力受限」，
中間帶很薄。**在程式碼生成上重現了同一個形狀。**

## 窗口對候選預算 N 的依賴

用每題實測通過率外推 `oracle@N = 1−(1−p)^N`：

| N | oracle | 基線 | 窗口 |
|---|---|---|---|
| 4 | 0.789 | 0.750 | 0.039 |
| 8 | 0.808 | 0.750 | 0.058 |
| 16 | 0.820 | 0.750 | 0.070 |
| 32 | 0.824 | 0.750 | 0.074 |
| 128 | 0.825 | 0.750 | **0.075（飽和）** |

基線固定於 N=8 的值，因為最大叢集在更多抽樣下只會更銳利地收斂到**眾數行為**
——眾數是否正確正是 `baseline_correct` 已經量到的事。

**結論：增加 N 唯一可能的幫助，是救回那 7 個能力牆題目**（若其真實通過率
小而非零）。8 次抽樣無法分辨 p=0 與 p=0.05。該實驗（每題 +32 候選）進行中，
是本閘門的最後一塊；結果將決定 G1 是確定性失敗，還是在 n≈100 下可能通過。
